# Engineering PRD: Knowledge Reconciliation Engine (formerly KUP v2.0)

**Version:** 2.1  
**Priority:** P0  
**Owner:** Knowledge Platform  
**Depends on:** MRI System Architecture v1.0, MRI Data Dictionary v1.0, Persistent Variable Registry

---

## 1. Objective

Refactor the legacy Knowledge Update Processor (KUP) into the **Knowledge Reconciliation Engine (KRE)**.

The KRE must cease all LLM and Markdown-parsing responsibilities. It is a **domain service responsible for reconciling evidence into accepted knowledge**. Its sole responsibility is to translate raw `ExtractedFact` entities (generated by AKE) into finalized, versioned `CompanyKnowledge` entities, ensuring traceability, consistency, and adherence to the single active thesis invariant.

---

## 2. Design Philosophy & Domain Flow

**Key Principle**: KRE executes strictly at the `(company_id, document_id)` aggregate level. One document, one transaction, one outcome.

```text
ExtractedFact (from AKE) 
       + 
Variable (Canonical)
       ↓
Knowledge Reconciliation Engine
       ↓
Compare with current CompanyKnowledge
       ↓
KnowledgeUpdateTransaction (with explicit Operations)
       ↓
Workspace Updater (Executes Operations)
       ↓
CompanyKnowledge (Updated & Versioned) + KnowledgeHistory (Audit)
```

---

## 3. Goals and Non-Goals

### Goals
- Refactor to consume the `ExtractedFact` and `Variable` tables.
- Generate explicit operations (ADD, UPDATE, SUPERSEDE, IGNORE, CONFLICT) for the Workspace Updater.
- Version `CompanyKnowledge` with `effective_document_id` and `effective_date`.
- Implement rigorous Confidence and Conflict policies.

### Non-Goals
- Modifying AKE's extraction logic.
- Executing Workspace updates itself (WorkspaceUpdater does this).

---

## 4. The Policies

### 4.1 Knowledge Confidence Policy
Knowledge confidence is a derived metric, NOT just the raw AKE extraction confidence.

`Knowledge Confidence = Base AKE Confidence * Source Reliability Penalty * Recency Decay`

*Base Policy:*
- `Annual Report / Official Filing`: 1.0 multiplier
- `Concall / Management Interview`: 0.9 multiplier
- `MOSI / Broker Report`: 0.8 multiplier
- `Unofficial Blog / News`: 0.5 multiplier

### 4.2 Conflict Resolution Policy
- **Same Document Conflict**: If a single document extracts contradictory values for the same variable (e.g. 18% vs 40%), operation is `CONFLICT`. Handled via human review.
- **Cross-Document Conflict**: Newer document supersedes older document (`SUPERSEDE`). If documents have the exact same date, the higher source reliability wins.

---

## 5. State Machine: Reconciliation Logic

When KRE processes `(company_id, document_id)`:

For each `ExtractedFact` mapped to a `CANONICAL` variable:
1. **Lookup**: Fetch current `CompanyKnowledge` for `(company_id, variable_id)`.
2. **Compare**:
   - No current knowledge: `ADD`.
   - Current knowledge exists, values differ, new evidence is strictly newer/more reliable: `SUPERSEDE`.
   - Current knowledge exists, values differ, new evidence is older/less reliable: `IGNORE`.
   - Same document contradicts itself: `CONFLICT`.
   - Current knowledge exists, values match: `UPDATE` (just bumps version/recency).
3. **Transaction Build**: Append `KnowledgeUpdateOperation` to `KnowledgeUpdateTransaction`.

---

## 6. Repository Architecture Updates

### `KnowledgeHistoryRepository`
- `get_history(company_id: UUID, variable_id: UUID) -> List[KnowledgeHistory]`
- Crucial for answering "When did our view on X change?"

### `KnowledgeTransactionRepository`
- `KnowledgeUpdateTransaction` must now persist state: `PENDING`, `PROCESSING`, `COMPLETED`, `FAILED`, `ROLLED_BACK`.

---

## 7. WorkspaceUpdater

The `WorkspaceUpdater` should not know business rules. It blindly executes the operation plan provided by the KRE.

- `ADD`: Insert new `CompanyKnowledge` (Version 1).
- `SUPERSEDE`: Update `CompanyKnowledge` (Increment Version), Insert into `KnowledgeHistory`.
- `UPDATE`: Update recency/confidence on `CompanyKnowledge`.
- `IGNORE` / `CONFLICT`: No mutation on `CompanyKnowledge`.

All executed inside one atomic transaction.

---

## 8. Acceptance Criteria

1. KRE executes at the `(company_id, document_id)` level.
2. `CompanyKnowledge` carries strict versioning (`version`, `effective_document_id`, `effective_date`).
3. The `SUPERSEDE` operation is fully supported.
4. Confidence is calculated using the Reliability policy, not just raw AKE output.
5. `KnowledgeUpdateTransaction` persists its execution state (`PROCESSING` -> `COMPLETED`).
6. `KnowledgeHistoryRepository` is implemented for auditing.
